# ADR-026: API Gateway HTTP API as REST Entry Point

**Status:** Accepted
**Date:** 2026-05-18

---

## Context

The walking-skeleton deployment used an Application Load Balancer (ALB) as the single public entry
point for all HTTP traffic, routing to all ECS services via path-based listener rules. This was a
pragmatic simplification: the ALB was faster to wire than API Gateway + VPC Link, and all services
were walking-skeleton stubs that needed no authentication.

Two problems emerged.

**Cost.** The ALB has no free tier and costs $0.0225/hour fixed plus $0.005/hour per public IPv4
address (two ALB nodes × one per AZ). At a typical dev session pace (72 active hours/month), the
ALB alone accounts for ~$2.40/month — nearly half the $5/month budget. This accrues whether tasks
are running or not, for the entire duration the environment is up.

**Architecture gap.** The system overview (`docs/02-architecture/system-overview.md`) already shows
API Gateway HTTP API as the REST entry point, with the ALB reserved for WebSocket traffic
(realtime-service only). The walking-skeleton ALB was intentional technical debt. This ADR closes
it.

---

## Decision

Replace the internet-facing ALB with **API Gateway HTTP API + VPC Link + Cloud Map (ECS Service
Discovery)** for all REST services.

Network path after this change:

```
Internet → API Gateway HTTP API (public endpoint)
              ↓  JWT Authorizer validates Authorization: Bearer <token>
           VPC Link (private tunnel into the VPC, no public internet hop)
              ↓  routes via Cloud Map service discovery
           ECS task (public subnet, task IP registered in Cloud Map)
```

**WebSocket traffic is out of scope.** The realtime-service routes WebSocket connections through an
ALB per ADR-020. The ALB module is retained for that purpose and will be provisioned when
realtime-service development begins.

---

## JWT Authorizer

API Gateway runs a JWT Authorizer on every inbound request before routing to any downstream
service. On a valid token it extracts claims and maps them to forwarded headers. On an invalid or
absent token it returns `401` without touching any service.

| Config field | Value | Notes |
|---|---|---|
| Issuer | `https://auth.dev.collabspace.io` | Fixed string per environment — see below |
| Audience | `collabspace-api` | `aud` claim auth-workspace sets in issued JWTs |
| JWKS URI | `https://{api_gw_id}.execute-api.eu-central-1.amazonaws.com/.well-known/jwks.json` | Derived from API GW endpoint in Terraform |

**Why a fixed string for the issuer, not the API Gateway URL.** `make dev-down` destroys and
recreates the API Gateway on every session, producing a new auto-assigned URL. Tying the `iss`
claim to that URL would require updating auth-workspace's SSM config on every `dev-up`. The fixed
string `https://auth.dev.collabspace.io` does not need to resolve in DNS — API Gateway validates
the `iss` claim as a plain string comparison. The string is stored in SSM at
`/collabspace/dev/jwt/issuer` so auth-workspace can read it at startup.

**JWKS URI churn on dev-down/dev-up.** The JWKS URI references the API Gateway endpoint, which
changes with each recreation. This is harmless in practice: Terraform always reconstructs the JWT
Authorizer config consistently within a deployment. The previous session's JWKS URI is not reused.

### Public routes (no JWT Authorizer)

The following routes are exempted from the JWT Authorizer:

- `POST /auth/register`
- `POST /auth/login`
- `GET /.well-known/jwks.json`
- `GET /actuator/health`
- `GET /notifications/health`

Everything else requires a valid JWT.

## Internal token

API Gateway injects `X-Internal-Token` into every forwarded request via a stage variable. The value
is a random 32-character string generated by Terraform (`random_password`) at environment creation
and stored in SSM at `/collabspace/dev/api/internal-token`.

Downstream services validate this header on every request and return `401` if it is absent or
incorrect. This prevents requests that arrive inside the VPC but bypass API Gateway from being
processed, even from other ECS tasks.

See `docs/02-architecture/api-gateway-trust.md` for the full trust model.

---

## VPC Link and Cloud Map

API Gateway HTTP API VPC Link (v2) has **no hourly charge** — only data transfer is billed
($0.01/GB). This is distinct from the REST API (v1) VPC Link which charges $0.01/hour.

The VPC Link routes requests to ECS tasks via **ECS Service Discovery (Cloud Map)**. Each ECS
service registers an `aws_service_discovery_service`; ECS registers task IPs in Cloud Map at task
start and deregisters them at shutdown. API Gateway resolves live task IPs through the VPC Link at
request time, round-robining across registered entries.

Cloud Map health checking uses `health_check_custom_config` (driven by ECS task state) rather than
a Route 53 health check, which would cost $0.75/endpoint/month.

**Consequence for health checking.** The ALB performed active HTTP health checks
(`/actuator/health` every 30 seconds). That mechanism is gone. ECS still restarts tasks that exit
unexpectedly, and Cloud Map deregisters tasks that ECS marks unhealthy. Adding a container-level
`healthCheck` block to each ECS task definition is a follow-up item per service.

## Security group changes

| Before | After |
|---|---|
| ECS tasks: inbound from ALB security group | ECS tasks: inbound from VPC Link security group |
| `alb_to_ecs` egress rule on ALB SG | Removed (ALB no longer routes to ECS tasks) |

A new `vpc_link_sg` security group is created in the security-groups module and attached to the VPC
Link ENIs. The ECS tasks security group's inbound rule is updated to reference `vpc_link_sg`. The
security group-to-security group reference pattern is preserved — no CIDR-based rules.

The ALB security group is retained in the security-groups module for the future realtime-service
ALB.

## Alternatives considered

**Keep the ALB.** The ~$2.40/month ALB cost remains and the architecture gap against the system
overview persists. The walking-skeleton ALB was always temporary; this is the planned migration.

**API Gateway + private ALB (production target pattern).** `api-gateway-trust.md` describes the
production path as API Gateway → VPC Link → ALB → ECS. Keeping a private (non-internet-facing) ALB
adds active HTTP health checks and ALB-weighted routing but costs identically to the public ALB.
For dev, the extra capability does not justify the cost. This is the correct pattern for
staging/prod once those environments are provisioned.

**API Gateway WebSocket API for realtime-service.** Rejected per ADR-020. The EC2-based
realtime-service does not fit the Lambda/HTTP-integration model that API Gateway WebSocket API
requires.

---

## Consequences

**Positive:**
- Closes the architecture gap — deployed topology matches `system-overview.md`.
- JWT validation moves to the edge — services no longer receive unauthenticated requests.
- ~$2.40/month cost reduction at the current dev session pace.
- Services can trust `X-User-Id` and `X-User-Workspaces` headers without re-validating the JWT
  (see `api-gateway-trust.md`).

**Negative:**
- Active HTTP health checks are gone. Follow-up: add a container `healthCheck` block to each ECS
  task definition.
- Services must now validate `X-Internal-Token` on every request. This is the first header-based
  security control services are responsible for enforcing.

---

## Revisit when

- Moving to staging/prod: add a custom domain, TLS termination, and the private ALB for the VPC
  Link layer (matching the `api-gateway-trust.md` production pattern).
- realtime-service development begins: provision the ALB module for WebSocket traffic. Routing and
  auth flow for WebSocket connections are documented in ADR-020.
