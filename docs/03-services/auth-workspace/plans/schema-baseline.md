# Plan: schema-baseline

**Feature branch:** `feat/auth/schema-baseline`
**Tier:** Full
**Service:** auth-workspace

---

## 1. Slice statement

The `users` table exists in the database with the correct schema, enforced by Flyway, verified by integration tests. No application code is implemented in this slice.

## 2. User-visible behavior

None directly. This slice is a schema prerequisite for user registration. The service starts without error and `/actuator/health` continues to return `{"status":"UP"}` after the migration has been applied.

## 3. API contract

N/A — no endpoint is added in this slice.

## 4. Data model changes

**Migration:** `V1__create_users.sql`

**Table: `users`**

| Column          | Type          | Constraints                        | Notes                                              |
|-----------------|---------------|------------------------------------|----------------------------------------------------|
| `id`            | `uuid`        | PK, not null                       | Generated by the application (not DB default)      |
| `email`         | `text`        | unique, not null                   |                                                    |
| `password_hash` | `text`        | nullable                           | Null for future OAuth users; never logged          |
| `name`          | `text`        | not null                           | Single display name field; no first/last split     |
| `created_at`    | `timestamptz` | not null                           |                                                    |
| `updated_at`    | `timestamptz` | not null                           |                                                    |

**Out of scope for this migration:** `workspaces`, `memberships`, `refresh_tokens`.

Role does not belong on `users` — role is workspace-scoped and will live in `memberships` when that table is added.

## 5. Validation rules

N/A — no input validation at the migration layer.

## 6. Edge cases

| Scenario | Expected result |
|---|---|
| Fresh database — `flyway migrate` runs for the first time | Migration applies cleanly; `users` table exists with all columns and constraints |
| Already-migrated database — `flyway migrate` runs again | No-op; Flyway detects checksum match and skips; no error |

## 7. Authorization

N/A — no endpoint, no auth surface.

## 8. Observability

- Flyway logs each migration applied at startup (e.g. `Successfully applied 1 migration to schema "public"`).
- `/actuator/health` DB component continues to return `UP` after migration.
- No new log lines introduced in application code.

## 9. Out of scope

- `workspaces`, `memberships`, `refresh_tokens` tables — added when their respective features are implemented.
- Any application code: no domain model, no repository, no controller in this slice.
- `POST /auth/register` endpoint — next slice.
- `username`, `avatar_url`, `first_name`/`last_name` columns — added if and when the feature that needs them is built.
